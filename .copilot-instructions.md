# Copilot Instructions for Practice Livewire

## Project overview
- This repository is a Laravel 12 application using PHP 8.2, Livewire 3, Volt, Tailwind CSS, Vite, and MySQL.
- Prefer Laravel conventions over custom abstractions.
- Keep business logic in the Laravel layer where it belongs: model scopes/attributes, policies, services, and controllers. Avoid dumping logic into Blade files or ad-hoc JS.
- The app is a user-scoped task manager with authentication, authorization, task deadlines, notification features, and UI interactions built primarily with Livewire.

## Core stack and conventions
### Backend
- Use PHP 8.2 features idiomatically and follow PSR-12 style.
- Use Eloquent models and query scopes for filtering/sorting logic instead of duplicating SQL in components.
- Put authorization rules in `app/Policies` and enforce them with `Gate::authorize()` or `authorize()` in Livewire actions.
- Prefer model accessors/attributes and `casts()` for computed status fields (deadline, completion, priority, etc.) rather than duplicating logic in views.
- Keep route-level middleware appropriate: authenticated pages should use `auth` or `verified` middleware.

### Frontend
- Use Livewire for stateful UI and server-driven interaction; avoid unnecessary custom JavaScript.
- Use Alpine.js only for minimal client-side enhancements when a Livewire-only solution is not practical.
- Use Tailwind utility classes as the default styling approach.
- Use Vite for assets and keep the front-end build configuration minimal and consistent.
- Prefer reusable Blade components or Livewire components for repeated UI blocks.

### Data and model design
- Treat the `Task` model as the source of truth for search/filter/status logic.
- Add query scopes for filtering (`filterBySearch`, `filterByPriority`, `filterByStatus`, etc.) instead of performing repeated if/else logic in components.
- Normalize nullable values and empty string handling in model accessors/casts.
- Keep user ownership checks strict: tasks should only be editable/deletable by their owner.
- Use database constraints and validation to prevent invalid states.

## Development best practices
- Follow Laravel ecosystem best practices and keep code readable, testable, and explicit.
- Prefer small, focused components and methods over large monolithic Livewire classes.
- Use validation before mutating data. For Livewire actions, prefer `$this->validate()` or dedicated request classes when appropriate.
- Keep UI logic and business logic separate. Components should orchestrate state and call model/policy logic, not own too much domain logic.
- Handle edge cases around deadlines carefully: overdue, due soon, completed tasks, and no-deadline tasks should behave consistently.
- Preserve user experience by providing clear empty states, loading states, and accessible UI.

## Security and authorization
- Never allow a user to access or mutate another user's tasks.
- Use policies (`TaskPolicy`) for ownership checks and keep `viewAny`, `view`, `restore`, and `forceDelete` behavior explicit and safe.
- Do not trust client-side state for authorization decisions.
- Check authentication before exposing task-related routes or actions.
- Handle user-generated content safely, including headline text, descriptions, and filters.

## Notifications and background jobs
- If implementing reminder or push notification features, keep notification logic in Laravel Notification classes and queue-based workflows.
- Avoid duplicate notifications by tracking notification state in the database or task/user context.
- Keep scheduler and queue configuration aligned with the app's notification requirements.
- Use proper background processing rather than blocking user requests for email or push jobs.

## Testing expectations
- Write tests for behavior, not implementation details.
- Prefer Pest feature tests for authentication, authorization, task CRUD, filters, and notification flows.
- Use factories and seeders for realistic data creation.
- Cover edge cases such as: overdue tasks, due-soon tasks, no-deadline tasks, unauthorized updates, and duplicate notification prevention.
- Validate with `php artisan test` and relevant targeted tests before finishing work.

## Command and validation workflow
Before finalizing work, run the smallest relevant validation commands:
- `php artisan test` for Laravel behavior checks
- `php artisan pint` for formatting and consistency
- `npm run build` when frontend or asset changes are made

## Files and folders guidance
- `app/Models`: Eloquent models, casts, accessors, scopes, and relationship logic
- `app/Policies`: authorization rules
- `app/Livewire`: Livewire components and interactive behaviors
- `resources/views`: Blade templates and reusable markup
- `routes/web.php`: web routes and auth-protected endpoints
- `database/factories` and `database/seeders`: test data generation and seed definitions
- `tests/`: Pest tests

## Output style and implementation guidance
- Favor direct, maintainable code over clever patterns.
- Keep comments minimal but useful for non-obvious domain logic.
- Use Japanese-friendly localization and user-facing strings when appropriate for this project.
- When updating task views or filters, maintain the existing semantics around completion, priority, deadline, and overdue status.
- Do not introduce unnecessary dependencies or large frontend frameworks when Livewire + Tailwind are sufficient.

## Summary
When implementing changes, align with the repository's established patterns:
- Laravel-first architecture
- Livewire-driven interactive UI
- Eloquent-powered business logic
- Tailwind-based styling
- Policy-based authorization
- Testable behavior with Pest

This project values practical, maintainable code that fits the Laravel + Livewire ecosystem rather than generic JavaScript-heavy approaches.
